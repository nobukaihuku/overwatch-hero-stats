# ヒーロー統計の修正報告とWEB側への対応依頼

2026年10月5日。対象はデータリポジトリ `nobukaihuku/overwatch-hero-stats` と、そのデータを利用する `overwatch-strategy-site` です。Astraの設計に沿って、SoLが収集処理を修正しました。

WEB側では、**過去分を含む統計値の正規化とエメラルドの表示対応**をお願いします。収集側を修正しても、既存JSONの負の値とWEB側のランク定義は残るためです。サイトはローカル開発中で、公開URLはありません。本番公開や日次再ビルドの有効化は今回の対応に含めません。

## 収集側は無効値の扱いと再試行を修正

収集元はBlizzard公式の `/ja-jp/rates/data/` です。PCとConsole、31マップ区分、3地域、QP全体と競技9ティアを組み合わせ、1,860条件を取得しています。

今回の収集側の修正内容は次のとおりです。

- 勝率・ピック率・BAN率は、有限数かつ0以上100以下だけを有効とします。数値文字列と末尾の `%` は受け付け、`-1`、100超、空文字、`--`、数値でない文字列、真偽値などは `null` にします。0と100は有効です。無効値を0や100へ丸めません。
- 無効なセルがあってもヒーロー行は保持します。既存の品質検査で、必須指標の欠損を `collectionQuality.status = "partial"` と `missingMetrics`、`missingMetricCount` に反映します。QPではBAN率を必須指標にしない既存仕様を維持します。
- 空の行配列やヒーローID欠損も再試行に含めます。通常は初回1回と、全条件の巡回後に最大2回です。失敗フィルタの `attempts` には実際のリクエスト数を記録します。最初の競技フィルタでは候補の探査も含むため、3を超える場合があります。
- 要求したフィルタと公式応答の選択値が違う場合は、保存を止める既存の動作を維持します。公式競技モードの `rq=2` から `rq=1` への切替と、保存時の競技値 `rq="2"` も維持します。

JSONの基本構造とフィルタ数は変えていません。READMEのprivate表記は、現在のpublic設定に合わせて修正しました。`package.json` の `private: true` はnpmへの公開を防ぐ設定なので、そのままです。

## WEB側では読み込み時に過去分も正規化

まず `src/lib/hero-stats.ts` と、そこから参照する既存の読み込み・品質判定処理を確認してください。取得元JSONを画面用データへ変換する共通箇所で、最新分と過去分の両方に収集側と同じ数値規則を適用してください。画面ごとに別々の補正を加える必要はありません。

既存JSONの `collectionQuality.status` だけを根拠に値を信用しないでください。2026年10月4日の保存データでは、13マップ・17条件・27ヒーロー行に、合計81個の `-1` がありました。それでも品質情報は `complete`、`missingMetricCount` は0でした。同日の `all-maps` 全60条件には負値も `null` もありません。この日の既定表示が正常でも、過去系列やマップ別データの安全性までは保証できません。

受け入れ条件は以下です。

- `-1`、`"-1"`、100超、非数値などが、率やティアスコアの計算へ入らない。`"50garbage"` のような文字列を50として受け付けない。
- 欠損は0%と区別し、既存の欠損表示に合わせる。必要な指標が欠けるヒーローは、その指標を使う順位・スコア・集計から除外する。ほかの有効な指標まで捨てない。
- 前回比は比較する両方の値が有効な場合だけ算出する。時系列グラフで欠損を0として描画しない。
- 最新JSONだけでなく過去JSONにも同じ処理を通す。品質表示がある箇所では、旧JSONの `complete` をそのまま「欠損なし」の保証に使わない。
- 数値の0・100・通常の小数、数値文字列、末尾 `%` 付き文字列は維持される。

過去の保存JSONは、取得時の記録として今回書き換えていません。Git履歴の書換や全期間の一括補正も行っていません。WEB側の読み込み時の対処は、今後の収集結果が修正されても必要です。

## エメラルドを型と表示へ追加

収集側は既に `Emerald` を取得しています。WEB側の `src/lib/hero-stats.ts` にある `HeroStatTier`、`LADDER_TIERS`、`TIER_LABELS` と、それらの利用箇所を確認してください。

エメラルドをプラチナとダイヤの間に追加し、少なくとも `/stats/` のランク選択、ヒーロー詳細のランク別勝率、該当する系列取得に反映してください。保存データのキーは `Emerald`、日本語表示は「エメラルド」です。UIで選べるだけでなく、実際に `filters.tier === "Emerald"` の数値を表示することを確認してください。

## WEB側の検証は既存テストとローカル画面で実施

既存のテスト基盤を使い、無効値を含む過去・最新データ、nullを含む前回比、エメラルドの選択と数値の対応を回帰確認してください。収集側と同じ正規化規則を使い、新しい外部依存は不要です。

`http://127.0.0.1:4321/stats/` で全ランク・ブロンズ・エメラルド・GM+を切り替え、表示とヒーロー詳細への遷移を確認してください。ヒーロー詳細ではエメラルドの勝率と欠損を含むグラフも確認します。リポジトリで必須の検証を実行し、`prepublish:check` が引き続き必須であれば、それも実施してください。これらはローカル検証であり、本番公開の操作は不要です。
